## Scope

CORE-0 establishes only the reusable headless foundation:

- Python package/install metadata and a small CLI;
- versioned YAML/JSON config loading and deterministic normalization;
- structural outlet-adapter registry with `single_round_port`;
- normalized provider/result/provenance contracts;
- deterministic `constant`, `constant_vector`, `inline_profile` and scalar-timeseries `csv` providers;
- config-relative path semantics;
- prepared-run workspace layout, normalized-config snapshot and provenance manifest.

It deliberately does **not** add plume equations, field reconstruction, permit evaluation, Copernicus access or TEOS-10 conversion. Those remain owned by later seams.

## Decisions frozen here

### Strict schema-v1 boundary

The loader requires the stable SPEC-0 top-level concepts and rejects unknown top-level fields. Core-owned sections fail explicitly on malformed values rather than silently coercing unsupported structures.

YAML and JSON pass through the same normalizer. Normalized config identity is SHA-256 over canonical JSON, independent of YAML formatting.

### Config-relative paths

The contract already says relative paths resolve from the config file. Therefore the repository example now uses:

```yaml
workspace:
  root: ../workspace
```

because the example itself lives under `configs/`. No runtime special case is used to make the demo land at repository-level `workspace/`.

### Outlet adapter means structure, not qualified physics

CORE-0 registers `single_round_port` geometry normalization and explicit unsupported-type failure. Registration does not imply a plume solver exists. MODEL-1 owns the first qualified physics implementation.

### Provider boundary

Provider implementations return numerical records and separate provenance. The initial deterministic providers are local/offline so CORE-0 can close without credentials or network access.

The schema-v1 CSV provider is intentionally narrow: timezone-aware, strictly increasing scalar time series. Future profile/vector CSV forms can extend the same provider interface without changing callers.

Provider shape normalization is **not** TEOS-10 thermodynamic normalization. MODEL-1 still owes the conversion boundary from in-situ/practical-salinity inputs to the production thermodynamic state required by the near-field kernel.

### Prepared runs are evidence, not model results

`plume prepare` validates and normalizes config, resolves local providers, creates the run directory, writes `config.normalized.yaml`, and writes `manifest.json`.

The manifest records:

- schema/config digest and source path;
- package version and git identity when available;
- ENU/depth/angle coordinate conventions;
- outlet geometry;
- provider request/source/input digest summaries;
- criteria snapshot;
- workspace identity/warnings.

No existing run directory is silently overwritten. Provider resolution occurs before run-directory creation so a bad/missing CSV does not leave a partial run record.
